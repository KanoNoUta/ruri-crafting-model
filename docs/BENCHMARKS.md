# G1 评估口径

## 两组不同的比较

1. **旧神经网络 → G1**：同一 44,450 条历史留出状态，技能标签一致率、Top-3、剩余技能次数 MAE。
   历史延迟是同一服务器、CPUExecutionProvider、单线程、batch 1、预热后交替 30 块 × 128 个状态。
   历史记录未留存该服务器 CPU 型号，不能把它当作 7800X3D 的测量。
2. **原生搜索 → G1**：本次 7800X3D / Windows CPU 小规模配对续作。原生实现是框架公开的
   GlobalParetoSearch 和 DeterministicBeamSearch，采用每步 1,000 ms、60,000 节点、深度 64、beam 24。
   `AllowStochastic=false` 是搜索器的在线保守设置；模型在规则允许的动作中预测，包括概率技能。
   这比较两个实际策略的输出，不是为二者强制设置相同搜索空间或证明能力。

## 状态选取

从原历史留出集分为 ordinary / expertStrict / cosmicEstimated 三组，
以 sampleId 的 SHA256 排序，每组取八个不同配方的首个状态。
先冻结 24 个状态，再评估模型，原始目标、装备、初始与中间品质均保持。
这是每层八个状态的等权测试，不代表全游戏配方出现频率；跨层可能属于相同配方。
数据集以曾通过教师筛选的状态为主，有成功样本选择偏差。

## 响应时间

载入和预热后，对每个保存状态测 30 次模型完整决策并取中位数；
原生搜索每状态测一次，再比较两个数组的中位数。
模型含特征编码、掩码构建、ONNX、argmax；原生含求解计算并返回首个建议。
两者排除 IPC、进程启动和模拟器。原生可能返回无建议，因此这是响应计算开销，
不能称作有效完整方案的单位生成成本。

`193.00935 / 0.1701 = 1134.68` 只是本次固定起点响应中位数之比。
续作中的两方法访问不同状态，因此其每步总体中位数另行记录，不替换相同起点的对照。
本次最终计时与编译、训练测试分开运行，避免将本任务自己的验证负载混入最终测量；
未采用系统级独占调度，环境噪声与未来重复测量仍会影响数值。

## 续作与技能次数

每状态两个固定随机种子，均使用相同步号的均匀随机数来抽取各自动作的结果。
动作不同，结果分布和终止位置也可能不同；这是 common-random-number 配对。
每步重新从模拟器观察状态，最多 60 次技能调用。没有外挂游戏、网络通信、宏缓存或模型回退。
达标 = 进度完成且达到原目标最低品质；软品质目标仅以完成进度作为达标，品质原值保留。
无建议、非法建议、未完成、未达品质、步数耗尽都不算成功。

本次两方法各 32/48 达标；模型普通/严格专家各有一次失败，搜索两组均达标，
宇宙概率状态模型 2/16、搜索 0/16。两种子共享起点，不能把 48 条轨迹当成 48 个独立配方。
这些是随机模拟结果，不是全分支验证，不应作为稳定概率估计。

技能次数只在共同达标的 30 对轨迹中比较：搜索中位 3，G1 中位 4。
不能拿各自不同的成功子集来宣称模型减少了制作技能。
累计计算时间受各自停止位置影响；没有测电能、云费用、128 核教师速度或训练速度。

## 独立验证

运行 `python scripts/validate_evidence.py` 可从逐轨迹记录重新核对分母、达标数、
配对技能次数、哈希以及历史分组加权指标。图表由 `scripts/render_charts.py` 从同一 JSON 生成。
图表使用零起点条形图；延迟采用明确标注的对数散点图，完整展示 24 个起点。

## 时间与计算开销总览图

运行 `python scripts/render_solver_comparison.py` 生成 `assets/solver-comparison.png`，
用于 README 的传统本地搜索与 G1 总览。两面板均采用零起点条形图，并直接标注数值：

- 单次决策时间：从全部 24 条 `sameStateDecisionTimings` 分别计算 `nativeSearchMs`
  与 `modelDecisionMedianMs` 的中位数，单位为毫秒；比值约 1,135 倍。
- 续作累计计算开销：从每种方法的 48 条 `trajectories` 累加全部 `decisionMs`，
  除以 1,000 转为秒，包含失败与提前停止的轨迹。

后者是各自运行的计算开销记录，两方法访问的状态与动作数不同，不能解释为同等工作量吞吐、
有效方案生成效率、完整制作速度或费用的加速倍数。逐状态差异仍由原有延迟散点图展示。
